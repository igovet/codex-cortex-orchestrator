# Phase D: exact-session observation lifetime root cause

**Status: source correction implemented; candidate/live qualification remains pending.**

## Exact failure mechanism

The first `events` read validates the receipt-selected candidate payload and
then imports its catalogue modules in order to calculate the catalogue
identity. That import runs with ordinary Python bytecode writing enabled. It
creates generated bytecode inside the installed, content-addressed candidate.

The candidate payload digest intentionally includes every regular file and
therefore treats that generated bytecode as a payload change. The first read
succeeds because digest validation happens *before* the import. The second
read revalidates the same receipt-selected candidate, sees the extra bytecode,
and correctly rejects it as a payload mismatch. The helper deliberately
returns only its sanitized “runtime-owned event generation is unavailable”
code.

This is why startup registration can be visible once and then observation
disappears during the same valid live session.

## Eliminated alternatives

The retained owner-only state establishes the following without exposing raw
nonce, generation identifiers, prompts, reports, or event bodies:

| Hypothesis | Result | Evidence |
| --- | --- | --- |
| Intent was not consumed | Excluded | Lease identity matched the authoritative isolated receipt. |
| MCP process did not claim the generation | Excluded | Exactly one process registration was retained. |
| Initialization failed to publish readiness | Excluded | Matching request and ready records existed with a bounded non-empty event file. |
| Process registration changed the ready binding | Excluded | Active lease registration matched the ready receipt; request/ready identities matched. |
| Lease TTL elapsed | Excluded | The failed second read occurred immediately after the successful registration read, far inside the configured lease interval. |
| Event rotation/replacement or lock race | Excluded | Request, ready, and event files remained owner-only regular files with stable inode identities. |
| Stop timing caused the failure | Excluded | Cleanup changed the lease to revoked only after the event reader had already returned unavailable. |

The candidate contained one generated bytecode file below its `scripts` tree.
The post-launch runtime receipt verifier reported a candidate-payload mismatch.
The observer's catalogue import is the state-changing action between the first
successful verification and the second failed verification.

## Architectural correction

Candidate observation must be read-only in fact as well as intent:

1. Launch every observer/import helper with bytecode generation disabled, and
   set the equivalent process-wide no-bytecode policy before any candidate
   module import.
2. Do the same for the installed MCP server and all candidate-side support
   processes; a content-addressed package must never self-mutate at runtime.
3. Retain the existing fail-closed digest check. Do **not** ignore bytecode or
   relax recursive payload verification, because that would make candidate
   tampering invisible.
4. Make bytecode-free execution an explicit candidate-runtime invariant, not a
   best-effort launcher convention.

## Implemented boundary

The packaged MCP declaration invokes `python3 -B ./scripts/cortex.py`. The
server, observation helper, and live observer also set
`sys.dont_write_bytecode=True` before dynamic imports; helper subprocesses use
an explicit `-B`. Payload verification remains recursive and exact, so a
deliberately introduced `__pycache__`/`.pyc` remains a candidate-tree mutation
and fails closed rather than being ignored.

## Required regressions

- Execute `events` at least twice against one live candidate generation and
  assert both reads succeed while the file inventory/digest is unchanged.
- Initialize and use the real stdio MCP server, then verify the installed
  candidate has no generated bytecode and still matches its receipt.
- Inject a bytecode or any other extra file deliberately after candidate
  staging; prove the second observer read fails closed.
- Preserve the complete focused live gate: initial `server_ready`, task
  opening, hidden worker events, clarification hold/record, continuation, and
  publication must all remain observable over the session lifetime.
