- The plugin’s machine-readable contracts live under [plugins/cortex](../../plugins/cortex/), including the manifest, MCP configuration, profile registry, and hook configuration.
- [profiles.json](../../plugins/cortex/profiles.json) is the canonical machine-validated source for all 21 exact profile names, descriptions, sandboxes, automatic/manual route categories, gates, `select_when`, `avoid_when`, adaptive model/effort routing, ordered implementation rules, scope/plan gate briefings, and shared report fields. Profile TOMLs must match its identity, description, and sandbox. Generated worker prompts layer the selected playbook, overall task context, and current gate mission/criteria; explicit coordinator overrides win over gate defaults.
- Automatic implementation routing uses bounded explicit signals from objective, requirements, acceptance criteria, scope, allowed paths, and verification. It applies the ordered specialist rules from `profiles.json` and uses `general` only as the conservative fallback. Planner/explorer evidence is advisory: the coordinator alone decides whether it justifies changing not-yet-started future waves, and records a concise reason. Planner and explorer prompts and the root orchestrator skill receive the generated canonical roster.
- The compact public worker `profile` field enumerates all 21 canonical names; legacy aliases are compatibility input only. A phase/profile mismatch is rejected before ledger writes. Dispatch metadata exposes phase, profile, capability, sandbox, and selection reason separately from unchanged native call arguments.
- `cortex/report/v1` payloads contain exactly seven fields: `summary`, `findings`, `questions`, `changed_files`, `tests`, `evidence`, and `uncertainty`; there is no worker `next_action` field. Findings record observed facts and evidence, not remediation instructions or target-gate decisions. The server sanitizes report data before persistence. See [cortex.py](../../plugins/cortex/scripts/cortex.py).
- Every gate report must carry a separate top-level `gate_result` envelope with the
  decision, failure class, findings, verification, and workspace. It is the
  canonical gate outcome for every phase; `closure` remains only a temporary
  review/close compatibility alias and never enters the strict report object.
- Report persistence is locally bounded: one report is at most 64 KiB and one attempt can publish 32 reports. There is no task-wide report-count or aggregate-byte quota; long-running tasks retain their immutable report history in SQLite until project storage is unavailable or explicitly pruned. Stranded-report recovery allocates a new record and never overwrites an authoritative record.
- Ledger, report-bus, journal, and lifecycle-telemetry paths reject symlink traversal and require regular-file targets before reads or writes. Report JSON is authoritative; `reconcile_report_bus` repairs derived indexes, receipts, and Markdown after an interrupted multi-file publication.
- The coordination ledger is host-private: it defaults to `~/.codex/cortex/projects/p-<sha256>/` and accepts only a private, outside-workspace `CORTEX_HOST_STATE_DIR` override. A legacy project-local `.codex/cortex` database is moved only by validated same-filesystem atomic rename; unsafe, non-database, split, or cross-filesystem legacy state fails closed.
- Completion is evidence-driven: reports require exact gate acceptance/verification PASS evidence; executable phases require structured checks; changed files reconcile against the per-attempt baseline; implementation phases must change real files and read-only phases must not. Metrics telemetry is not part of the canonical runtime contract.
- The v5 registry contains nine MCP operations. The ordinary Desktop compatibility projection exposes all nine, which makes `$cortex:orchestrator` operational without host-specific routing. Explicit launch-time `coordinator` and `worker` audiences each expose exactly five: coordinator `start_orchestration`, `continue_orchestration`, `manage_orchestration`, `manage_governance`, and scoped `read_worker_report`; worker `worker_question`, file-creating `get_report_template`, atomic `record_report`, exact immutable-briefing fallback `read_dispatch_briefing`, and scoped `read_worker_report`. Worker profiles and briefings prohibit lifecycle calls in compatibility mode; use the explicit worker projection when the host needs transport-enforced denial. Template creation writes one private fully structured JSON file and returns only its ref/path metadata. Workers edit that same file or send a small merge patch or complete replacement through `record_report`; invalid records keep it without consuming an attempt, while successful recording revalidates and atomically commits before deleting the draft. Both content reads are cursor-paged and server-bounded: a briefing fallback requires the complete project/task/attempt/profile/dispatch/digest tuple, and an incomplete response may continue only with its signed cursor. It cannot list or select another ledger artifact. A successor may read only report refs explicitly supplied in its dispatch, with exact `project_root`, `task_ref`, `attempt_id`, and `profile`; ungranted refs are rejected and worker context receives no coordinator Markdown-link instruction. Native `spawn_agent` and user-authorized `create_thread` remain host calls, not public MCP tools.
- Full governance resolves to an immutable policy snapshot and adds at most two server-owned lifecycle waves: `governance_activation` before ordinary work and `governance_close` before final `close`, both owned by `code_reviewer`. The resolver rejects `off` for C2/C3 and for stated risk triggers; `required`, C3, and the documented security/privacy/credential, destructive, migration, external-action, contract-integrity, linked-task, long-lived-lane, and multi-session triggers resolve to `full`. The MCP process audience is fixed at launch: unspecified transport uses the nine-operation compatibility projection, while explicit `coordinator` and `worker` audiences expose their strict five-tool projections.
- `task.plan_approval` accepts `auto` or `required`, defaulting to `required` for ordinary C2/C3 user tasks. Knowledge routes (`harvest` and `harvest-refresh`) force `auto`: they retain an internal planning phase, but never pause for post-plan user approval. Approval is available only after the final `plan` wave and records the plan revision, planner report ref, verified predecessor digest, and semantic future-pipeline digest. Material replanning preserves history, resets to `pending_plan`, and requires a replacement Planner plus fresh approval; no-op and transport-only changes do not invalidate approval. A required hold is resolved through `manage_orchestration(intent="plan_approval", payload={"decision":"prompt"})`, which returns a detailed `cortex/chat-interaction/v1`. The coordinator renders the objective, work packages, paths, dependencies, verification, risks, remaining phases, approve/revise/cancel meanings, and visibly labelled LLM recommendation as one final ordinary chat message, invokes no UI tool, and ends the turn. The next user message includes the opaque request ID when recorded; revision feedback is preserved verbatim, stale responses fail closed, cancellation remains pending, and silence never approves. All task types require observable task acceptance and verification criteria; Planner Scope domains and Planner Plan microtasks require complete acceptance and verification criteria too.
- Planner reports may carry a separate `planning` object with exactly `overview` and `work_packages`; this does not change the strict seven-field `cortex/report/v1` report. Packages require `id`, `title`, `objective`, and non-empty microtasks (plus optional paths/dependencies); every microtask requires `id`, `title`, `objective`, an explicit worker `profile`, narrow non-broad `allowed_paths`, acceptance criteria, and verification (plus optional dependencies). Microtask IDs are globally unique within a plan; `depends_on` may reference a microtask in another work package, and the combined microtask graph must remain acyclic. Unknown dependency references are rejected. Cortex validates dependency DAGs and bounds the catalog at 32 packages, 32 microtasks per package, and 128 total microtasks. The read-only Planner proposes the catalog; Cortex writes immutable, revision-scoped planner overviews at `planning/revisions/plan-<report-ref>/overview.md` and package artifacts under the same revision. The SQLite task document `planning_current` is the sole current-plan pointer; there are no `planning/manifest.json` or `planning/overview.md` latest aliases. After approval, Cortex topologically compiles the catalog into an immutable executable plan unit; it does not dispatch a generic implementation mission or broad `.` path.
- The coordinator builds or consciously accepts the initial pipeline, follows the returned snapshot by default, and alone changes future waves when verified evidence materially changes the work; planner/explorer recommendations are advisory. Human aliases such as `implement` and `build_verification` normalize to `implementation` and final `close`, respectively, and do not create retry waves.
- Public `continue_orchestration` infers rework when `future_waves` reintroduces a current or completed phase; callers do not need to remember `rework=true`. The initial `pipeline_obligations` are durable, and a replacement cannot silently discard a pending `implementation` phase: context-only repairs narrow dependencies while retaining delivery. `replan_count` is lifetime audit data and the legacy `replan_limit` is compatibility metadata, not an execution budget: every material public replan is grounded in a durable worker result or explicit recovery state. Per-gate counts and strategy names are audit and escalation evidence only; corrective cycles remain unbounded while acceptance or findings require work. The complete plan-approval and rework shape is preflighted before any attempt, gate, approval, or pipeline mutation. A stranded active task with no live or pending dispatch may use Planner-first `manage_orchestration(intent="resume", payload.future_waves=...)` recovery; ordinary active resume and recovery while a worker is live remain rejected. A legacy task persisted by an older runtime with an exhausted closure-rework marker is atomically restored through a Planner-first pipeline followed by every originally required implementation, QA, security/performance, review, documentation, and close phase, with stale downstream proof invalidated and fresh plan approval required. New tasks never create that attempt-budget marker. Before documentation or close dispatch, an accepted planning catalog is matched to non-invalidated delivery attempts; a missing implementation or required successor check triggers the same graph repair instead of another writer. Validation failures explicitly report `attempt_budget_consumed=false`; recorded failures raise effort/model routing but never consume a finite pipeline budget.
- Every profile has a machine-validated execution contract: required inputs, owned project artifacts, and a completion deliverable. The dispatch carries the attempt baseline rules and sandbox; read-only profiles and read-only phases must not report claimed `changed_files`. Their Python checks use `PYTHONDONTWRITEBYTECODE=1`, test/build caches are disabled where possible, and cleanup commands are forbidden. The validator retains manifest-recognized cross-language ephemeral outputs (conventional generated directories/roots/files, virtual environments, recognized build-output directories, and bytecode suffixes) as audit evidence, including matching conventional paths listed in `.gitignore`; arbitrary `.gitignore` outputs and unrecognized artifacts remain failures. Completion is accepted only when the required artifact and verification evidence exist.
- Completed tasks are immutable. To correct a completed task, use `manage_orchestration(intent="follow_up")` with its exact source `task_ref` and the user's exact corrective `payload.user_request`; Cortex creates a linked corrective task with a new ref. Source handoff and report Markdown paths are historical context only and must be revalidated against current source/tests. An active or blocked task uses `manage_orchestration(intent="steer")` with the original `user_message` and canonical English `message_en` when needed; Cortex records a task revision and returns resume calls only for addressable native worker sessions. `follow_up` rejects active sources. `payload.report_refs` is optional and bounded (at most 32 source refs); when omitted, Cortex selects a bounded recent set.
- The original user language belongs to the main coordinator only. Workers emit English in every message, tool argument, report, durable question, handoff, and native final; durable worker questions stay English. A worker that records a material question returns `QUESTION_RECORDED` plus a complete decision handoff: why input is needed, each full self-contained question, concrete outcome-based options with descriptions and trade-offs, and a recommendation. Every question requires a recommendation rationale and exact `recommended_option_ids`, or a concrete `recommended_answer` for text. The root renders the returned `cortex/chat-interaction/v1` completely in the user's language as one final ordinary assistant message, visibly labels the LLM recommendation, calls no UI/input/approval/elicitation tool, and ends the turn. The user's next message is recorded before the exact worker resumes. For a non-English task, the root may pass localized display projections without altering canonical values. The server rejects generic numbered, A/B, or recommended/alternative placeholders. Answers retain original value/language and require canonical `answer_en` for localized free text. Workers may submit 1–32 stable questions with `ask_batch` and poll one `batch_ref` with `poll_batch`; Cortex checkpoints accepted chat answers under the same durable ref. Revisions supersede unresolved batches. A corrective `follow_up` inherits the completed source task's `user_language`, but not a translated worker protocol.
- Parallel dispatches are issued in one model turn when supported and correlate
  by exact native `task_name`/`dispatch_ref` plus host child id, never ordinal
  position. While workers run, `waiting_workers` is silent and repeated wait
  timeouts do not produce heartbeat commentary.
- A worker fills the exact private report file created by `get_report_template` and calls `record_report` on the same `draft_ref`. Read-only workers use a small merge patch or complete replacement when their sandbox cannot edit `draft_path`. Invalid records keep the file and consume no worker attempt; the worker corrects and retries. `record_report` revalidates current state, atomically commits, and deletes the file post-commit. It returns only `REPORT_RECORDED report_ref=<value>` plus at most a two-sentence summary, or the exact tool error. Read-only workers report `changed_files: []`; ordinary shared-checkout source deltas are concurrency evidence. Manifest-recognized cross-language ephemeral output is retained as audit evidence—conventional generated directories/roots/files, virtual environments, recognized build-output directories, and bytecode suffixes, including matching conventional `.gitignore` paths; arbitrary `.gitignore` outputs remain failures. `read_worker_report` is repeatable, but only its first complete coordinator read after the matching durable native-worker stop returns `publication_required=true`, the derived Markdown link, and a bounded completion update. The coordinator publishes that link once, never alone, in the same user-language message as a short summary of what completed and what happens next. Early reads and rereads return no link and never authorize repeated publication. Human-visible worker labels are derived from the task domain in the user request, such as `Planner Authentication`; they contain no ordinal/digest, and gate mission verbs are not used as the module. The native host key is the lower-underscore profile/module plus ordinal and uniqueness digest (for example, `explorer_auth_02_<digest>`); that native key guarantees a new native session, while `followup_task` resumes only the same confirmed worker. Host spawn prompts de-duplicate the exact user request; `start_orchestration.next_action` precedes dispatch payloads, and the PostToolUse hook reasserts the first exact native spawn after that payload. The nested realistic harvest Planner prompt is regression-tested below 11,500 bytes and the complete public start response below 8,000 UTF-8 bytes. A worker is sent only after native `spawn_agent` returns a child id. A host wait-any form without explicit targets is allowed only while Cortex has a bound running child. `SubagentStop` recovers recorded reports and durable questions, but fails a no-report stop so compaction never waits on a dead child; PostToolUse recovery searches all matching reportless attempts in the current gate, preserving an earlier failure even if a later attempt completed. Every close report maps task acceptance and verification criteria to evidence; completion assertions alone are rejected.
- The control plane owns sequencing: it selects dynamic corrective waves, blocks environment or policy conditions, carries the originating report into corrective and originating-gate verification context, and requires that gate's finding to be resolved before downstream waves can start. A worker reports what it observed; it does not select the next action, remediation, or target gate.
- Any worker may publish a material decision with `worker_question`, return the question ref plus the complete decision handoff, remain resumable, and continue the same attempt only after the coordinator sends the detailed final chat question, stops, receives the next user message, and records that answer. Every choice permits optional free-form constraints. The server attaches every canonical answered question and answer to later reports as `resolved_user_decisions`; successors treat it as task-wide user authority and never repeat an equivalent decision under changed wording, keys, phases, or attempts unless the current user explicitly reopens it. Existing code is current-state evidence rather than desired-intent evidence; open blocking questions reject reporting and continuation.
- A dispatch grants the verified transitive frontier of its selected predecessor reports. A passed report covers only the exact refs supplied to and acknowledged by its attempt; covered history stays immutable in SQLite and remains part of the final Planner evidence digest. The worker reads and reviews every frontier handoff, reconciles conflicts against current evidence, and includes the generated `Predecessor review:` acknowledgement in report evidence; public `record_report` rejects omissions. Report bodies are paged through `read_worker_report`, not embedded in the briefing. `depends_on` selects exact earlier phases, omission means the frontier of all verified predecessors, and `[]` means intentional independence. There is no separate predecessor-count limit.
- Cortex automatically adds `docs/project/index.md` and `docs/features/index.md` to every worker briefing when present. The planner recommends task-relevant linked pages and the coordinator attaches them through public compact-worker `context_files`; every worker re-checks the indexes and records `Knowledge reviewed:` evidence. Documentation is navigation/prior rather than authority, so consequential claims are confirmed in source, tests, schemas, migrations, or executable configuration. Explicit context paths must be existing project-relative regular files; absolute, traversing, missing, and symlink paths are rejected.
- Preserve the opaque `task_ref` returned by a successful Cortex lifecycle call on every later task-scoped lifecycle and report-read call. Exact duplicate active starts are idempotent; different task/wave contracts may run concurrently below one project root. An omitted ref always fails closed with `task_ref_required`, never a project-wide task selection.
- Every task-scoped `continue_orchestration`, `manage_orchestration`, and recovery/read call must carry the exact `task_ref` from a successful lifecycle response. Unscoped management never inspects, lists, infers, or selects a project task; it fails closed with `task_ref_required`. A start response with `ok: false`, `task_created: false`, or no `task_ref` created no recoverable task, so the coordinator must stop and report the blocker rather than recover an older task.
- Start is called once per task contract and exposes `replayed`; a replay returns no dispatches and cannot trigger a duplicate wave. A lost original response is recovered once through management inspect. Confirmed project-scoped prune removes task state older than seven days and reconciles related indexes/claims/bindings without clearing recent state, lanes, source, docs, or plugin files.
- Codebase Memory is optional worker tooling. Every worker briefing supplies the project key precomputed from canonical `project_root` with the current `cbm_project_name_from_path` safe-ASCII/UTF-8-hex/FNV-1a-200 rule. Incremental work requires a current zero-gap coverage manifest; otherwise use the full scope/discover/architecture/plan/documentation/review/close pipeline, with Planner Scope producing up to eight non-overlapping discovery domains before the final Planner consumes all predecessor evidence. Domain-partitioned exploration, behavior-complete pages, evidence-backed exclusions, and independent zero-unmapped-surface review remain mandatory. - During active Cortex orchestration, the main/root agent is coordination-only: it may use lifecycle calls, exact returned dispatches, waiting, report evaluation, user communication, and safe recovery, but must never inspect, search, read, edit, patch, build, test, or run the target project, Cortex plugin source/cache, `.codex` state, or runtime internals. For every public tool, bundled instructions, public schemas, and exact returned responses are authoritative; code/cache inspection is forbidden. Workers own every project operation, and the root remains idle while they run. `SessionStart` and every public v5 `next_action` reassert this lock.
- Every Cortex participant maintains a turn-local evidence index and reads each exact skill or file path at most once per turn. Re-reading is allowed only after explicit truncation/pagination, an edit after the read, or a distinct unread range; unchanged content is reused.
- Structured public v5 `ok: false` validation and recovery responses are caller-correctable protocol outcomes, not MCP server exceptions, and are not appended to `~/.codex/logs/cortex-tool-errors.jsonl`. Worker callers retry named input/schema corrections on the same attempt without consuming recovery budget; only explicit non-retryable integrity, storage, permission, or unavailable-identity blockers terminate the attempt. Raised MCP-boundary exceptions remain redacted and logged.
- Mutating v5 calls use server-owned request-digest receipts for idempotent replay. An identical retry replays; stale steps, duplicate slots, missing slots, and changed continuation inputs are rejected before partial writes. A changed start contract creates a separate task. Public schemas do not require submission, task, wave, attempt, or host metadata. Profiles and aliases are preloaded/validated when the MCP server starts.
